Waterfall, Incremental or Agile: which model should build a citizen services portal?

A DevSecOps Lab microproject that compares three software development models by planning one hypothetical e-governance portal with each of them, then running it through a secured, automated delivery pipeline.

Case study: a simulated portal where citizens apply for services and track an application. The same requirements are used to show how each model would plan, build, test and release it.

SDG 9: Industry, Innovation and Infrastructure

SDG 9 calls for resilient infrastructure and innovation. Choosing a suitable development model, and automating testing and security checks, helps public digital infrastructure be delivered reliably and improved safely.

The three models

Waterfall

Work moves through fixed phases in order: requirements, design, implementation, testing, deployment. Each phase is completed and approved before the next begins.

In the portal: all form fields, status rules and admin reports are specified and signed off first. The portal is built and tested as a whole and goes live once.

Incremental

The system is divided into parts. Each increment goes through a mini plan, build and test cycle and is released, so the product grows in working slices.

In the portal: increment 1 is application submission, increment 2 is status tracking, increment 3 is the admin dashboard. Each release is tested together with earlier ones.

Agile

Short sprints deliver small, working changes. A prioritised backlog is refined continuously, and review and retrospective feed lessons into the next sprint.

In the portal: citizens' and officers' feedback on the simulated form and tracker reorders the backlog each sprint, for example adding a clearer error message or a mobile layout fix.

    DevSecOps workflow and security

    1. Plan backlog in Jira or GitHub Projects
    2. Code Git branches and pull requests
    3. Build and test Jenkins runs automated tests
    4. Analyse SonarQube static analysis
    5. Scan Trivy on files, dependencies and image
    6. Package Docker image, non-root
    7. Deploy Jenkins ships the image to an AWS EC2 server built with Terraform
    8. Monitor health check and logs

    Security controls in this project

    • Input validation and parameterised SQL queries.
    • Rejection of personal-data patterns.
    • Content-Security-Policy, nosniff and frame protections.
    • No secrets in the repository; placeholders in .env.example.
    • Container runs as a non-root user.
    • Pinned dependencies scanned by Trivy.

    Testing, scope and limitations

    Testing

    Automated API and validation tests in tests/ cover the pages, security headers, form validation, status tracking and synthetic data. Run them with the commands in the README.

    Scope

    Comparison of three SDLC models, a simulated citizen form and tracker, a synthetic admin view, and a reproducible CI/CD and cloud configuration.

    Limitations

    • No authentication, so the admin view is a demo only.
    • Status progression is time-based, not workflow-based.
    • Comparison is qualitative, not measured on a real team.
    • No rate limiting or HTTPS in the default setup.

    Future enhancements

    • Role-based login with hashed passwords and audit logs.
    • HTTPS via a load balancer or reverse proxy.
    • Quantitative model comparison using simulated sprint data.
    • DAST scanning (for example OWASP ZAP) in the pipeline.
    • Multi-language support for citizens.
